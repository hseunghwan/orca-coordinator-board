# Coordinator Board: 상세 동작 노트

영어 README에서 줄인 상세 동작, 코디네이터 운영, 전송 규칙, 실기에서 확인한 Orca 동작을 그대로 둔 문서다. 사용자 안내 요약은 [README](../README.md)와 [한국어 README](../README.ko.md)에 있다.

## 대시보드가 여는 파일

Orca 플러그인은 편집 영역에 자기 화면을 직접 띄울 수 없다. 그래서 대시보드는 `.coordinator-board` 파일 전용 에디터로 만들었다. 대시보드를 열면 워커가 지금 보고 있는 워크스페이스에 `.coordinator-board/board.coordinator-board`를 쓰고 그 파일을 연다.

- 파일에는 보드 데이터가 없다. 탭을 여는 열쇠일 뿐이고, 내용은 모두 워커에서 읽는다.
- git checkout이면 `.git/info/exclude`에 `/.coordinator-board/` 한 줄을 더해 git에 잡히지 않게 한다. `.gitignore`는 만들지 않는다.
- 다른 호스트(SSH 등)의 워크스페이스에서는 열지 않는다.
- 세션을 누르면 그 세션의 워크스페이스로 화면이 바뀐다. 대시보드 탭은 처음 연 워크스페이스에 남는다.
- 화면 배치는 Paseo판 보드와 같다. 보기는 인박스(기본), 집중, 매트릭스 가운데 고르고, 보기와 보드 언어(한국어 기본, English)는 이 기기에 저장된다. Paseo판의 기존(Classic) 보기는 두지 않는다. 이 기기에 기존 보기가 저장돼 있으면 인박스로 연다.
- 결정 카드에서 담당 세션에 바로 답장한다. 보내기 단축키는 macOS에서 ⌘+Enter, 그 밖에서는 Ctrl+Enter다. 긴 추천 답장은 **답장 전문 보기**로 펼쳐 읽어야 보낼 수 있다.
- **질문하기**로 결정 전에 그 세션에 물어볼 수 있고, 문답은 카드 아래에 쌓인다.
- **집중** 보기는 가장 급한 결정 한 건만 크게 띄운다. 위의 막대가 남은 결정과 처리한 결정을 보여 준다. J는 다음, K는 이전 결정으로 가고, S는 지금 결정을 이번 방문 동안만 맨 뒤로 미룬다. 입력창에 쓰는 동안에는 이 키를 듣지 않는다. 맨 아래 줄은 프로젝트별로 진행 중인 세션을 보여 주고, **진행 보기**로 세션 진행과 기록을 연다.
- 사이드바 패널은 집중 보기와 같은 순서의 카드를 그린다. 카드에는 우선순위 배지, 프로젝트와 세션 이름, 질문, 코디네이터 추천이 나온다. 선택지 버튼은 답장을 채우고, **답장 보내기**나 ⌘/Ctrl+Enter로 대시보드와 같은 경로(`board.send-decision`)로 보낸다. **이전**, **다음**, **나중에**로 카드를 옮기고, **나중에**는 패널이 열려 있는 동안만 카드를 맨 뒤로 미룬다. 권한 대기 결정은 **세션에서 승인** 안내와 **세션 열기**만 둔다. 결정 기록과 PR 카드는 내용만 보여 주고 답은 보드에서 한다. 사이드바 답장은 Orca 입력창 한도인 16384자까지다.
- **매트릭스** 보기는 위의 띠에 결정을 급한 순서로 놓고, 아래 표에 프로젝트마다 내 결정, 진행 중, 확인 대기, 대기 중, 완료 칸을 둔다. 칸을 누르면 그 줄 아래에 카드가 펼쳐진다. 호스트 칸은 이 기기의 세션 수만 센다. 좁은 화면에서는 프로젝트별로 접고 편다.
- 보낸 답장은 그 자리에 영수증으로 남는다. 지난 답장은 인박스의 **기록** 탭에서 다시 본다.

- **코디네이터에 요청**을 누르면 코디네이터 패널이 열린다. 코디네이터가 있으면 일을 맡기거나 다이제스트를 요청하고, 없으면 추천 설정과 시작할 워크스페이스를 골라 새로 시작한다. 결정 카드의 **코디네이터에 추천 요청**과 **코디네이터에 조율 요청**도 코디네이터가 있을 때 쓸 수 있다.
- 설정에서 기존 세션을 코디네이터로 지정하거나 해제하고, **새 코디네이터로 교체…**로 바꾼다. Orca는 플러그인이 사이드바 고정을 바꾸게 하지 않아 고정 설정은 없다.
- 결정 기록 카드에서는 코디네이터가 남긴 질문마다 선택지를 하나 또는 여럿 고르거나 직접 답한다. 답하지 않을 질문은 **이 질문 건너뛰기**로 넘긴다. 답은 운영 코디네이터나 담당 세션에 보내거나 **보드에만 저장**하고, 직접 확인할 일은 **확인했어요**로 닫는다. 받는 세션이 바빠 대기 중인 답은 카드에 남고 **전송 대기 취소**로 거둔다. **근거·이력 보기**에서 근거와 이전 문답을 보고, **기록 닫기**로 답 없이 닫는다.
- 병합할 수 있는 PR은 **보드에서 병합**을 눌러 대상 브랜치, 검토한 HEAD, 검사 상태를 확인하고 병합 방식을 골라 **병합 확정**한다. 병합되면 코디네이터에 후속 작업을 알리고, 그 결과는 영수증에 남는다. 병합 기록 카드는 PR 상태를 1분마다 다시 읽는다.
- 설정의 **프로젝트별 GitHub 저장소**에서 프로젝트마다 PR을 읽을 저장소를 직접 연결하거나 자동 감지나 끄기를 고른다. **사실 질문 자동 답장**도 설정에서 켜고 끈다.
- 사실 질문 자동 답장: 세션의 마지막 답이 "이 세션은 어느 프로젝트 소속인가요?" 같은 한 줄 사실 질문이면, 보드가 그 답을 만들어 다이제스트 때 코디네이터 명의로 보낸다. 코디네이터 터미널이 서명한 메일로만 보내고, 서명할 수 없으면 보내지 않는다.
- 결정 장부: 장부의 결정에 답하면 보드가 담당 세션이나 코디네이터에게 보낸다. 받을 세션이 작업 중이면 대기열에 두었다가 턴이 끝나면(Orca 상태 변화나 30초마다 확인) 한 번 보낸다. 대기 중인 답은 취소할 수 있다.
- PR 병합: 프로젝트마다 GitHub 저장소를 자동, 직접 지정, 끄기 중 하나로 연결한다. 병합은 미리보기(5분짜리 확인 토큰)와 확정 두 단계이고, 확정은 미리보기 때의 head 커밋으로만 병합한다. 보드가 병합하면 장부 담당이나 코디네이터에게 보드 메일 터미널 명의로 한 번 알린다.
- 결정 답장, 조율 요청, 질문, 결정 기록 답, 코디네이터 요청에 사진을 붙인다. 클립 버튼, 붙여넣기, 끌어 놓기로 JPEG, PNG, WebP를 4장까지(한 장 5MiB, 합계 12MiB) 넣는다. 기록 카드는 보드에 남은 사진을 **사진 n** 버튼으로 다시 본다.
- 설정의 **실행기**에서 실행기마다 배정 포함 여부와 새 작업 세션 권한을 고른다. 모델 목록은 제안이다. Orca는 플러그인에 실행기의 모델 목록을 주지 않는다. **계정별 남은 사용량**은 한도별 잔여량과 초기화 시각을 보여 주고 사용량 기반 자동 배정을 켜고 끈다. **모델 배정**은 난이도 A~D와 운영 M마다 후보 모델과 추론 강도를 순서대로 저장한다.
- 설정의 **다른 프로젝트의 세션 하나 연결**로 관리하지 않는 프로젝트의 세션 하나를 관리 프로젝트의 다이제스트에 넣거나 뺀다. 워커가 `board.hosts`를 주면 설정에 Orca 호스트 목록도 나온다.
- 진행 보기의 세션 카드를 펼쳐 **기록 추가**나 **기록 편집**으로 결정 요청, 확인 요청, 완료 근거를 남기고, 그 세션의 보드 보고를 켜고 끈다.
- 사진: Orca는 메시지에 그림을 붙일 수 없다. 보드는 사진을 Paseo처럼 데이터 폴더의 `session-photos/`에 저장하고, 메시지 첫 줄의 표식 바로 뒤에 사진마다 `[사진 1] <파일 경로>` 줄을 넣는다. 받는 에이전트는 그 경로의 파일을 연다. 같은 컴퓨터의 세션에만 보낸다.
- 보고: 코디네이터가 아닌 세션의 `coordinator-board report`는 그 세션의 보고 허용(카드의 보고 켜기, `board.set-reporting`)이 켜져 있어야 받는다. 보드가 배정한 작업자는 처음부터 켜져 있다. Orca에는 에이전트 메타데이터가 없어서 이 표시는 보드 데이터 폴더(`reporting.json`)에 둔다.
- 작업 단계: 보드가 배정한 작업은 작업 기록(`work-items.json`)을 하나씩 가진다. 기록은 `requestKey`, 완료 기준(`doneMeans`), 단계를 담고, 작업자가 첫 응답을 하면 그 세션에 이어진다. 단계는 진행 중, 입력 대기, 완료 보고됨, 검증 중, 완료, 방치, 사람 결정 대기 일곱 가지다. 같은 이벤트를 다시 받으면(재전달, 같은 보고 반복, 폴링 반복) 기록과 알림이 바뀌지 않는다. 이미 완료 보고됨이나 검증 중인 작업에 같은 완료 보고가 다시 오면 글만 바꾸고 단계와 시각은 그대로 두어 코디네이터에게 다시 알리지 않는다. 카드에 사람 기록이 있어도 작업자의 보고는 작업 기록에 반영된다(카드 기록만 그대로 둔다). Orca 상태는 진행 중과 입력 대기만 바꾼다. 턴이 끝났는데 완료 보고가 없으면 **완료 후보**로만 표시하고, 작업자가 `report --kind done`으로 보고하면 **완료 보고됨**이 된다. 완료는 사람이 카드 기록을 완료로 저장해야 확정된다. 진행 보기와 매트릭스에서 단계가 있는 카드는 단계를 레인보다 먼저 보여 주고, 완료 보고됨과 완료 후보는 확인 대기 칸에 놓는다. 결정 대기 카드와 사람이 완료로 표시한 카드는 그대로 둔다.
- 완료 확인: 완료 후보가 생기면 보드가 그 세션이 대기 중일 때 `[coordinator-board]` 머리말과 `{"type":"coordinator-board.done-check",itemId,doneMeans}`를 담은 문장을 한 번 보낸다. 같은 단계에서는 한 번만 묻는다. 세션이 보고 없이 답하면 그 답도 한 턴이라 새 완료 후보가 생기지만 다시 묻지 않고, 방치 기준이 판단한다. verify로 되돌아가 단계가 새로 시작되면 한 번 더 물을 수 있다. 세션이 `report --kind done`으로 답하면 완료 보고됨, `--kind question`이면 입력 대기, 이어서 작업하면 진행 중으로 남는다. 작업자가 보고에 GitHub PR 주소를 적으면 그 PR을 2분에 한 번까지 읽어, 병합되면 완료 후보(완료 보고됨이면 검증 중)로, 병합 없이 닫히면 완료 후보로 바꾸고 묻는다.
- 코디네이터 알림과 확정: 작업이 완료 보고됨이나 방치가 되면 보드가 코디네이터에게 `[Coordinator Board · 작업 …]` 문장을 한 번 보낸다. 코디네이터는 `coordinator-board verify --item <itemId> --result pass|fail --text-file -`로 확정한다. pass는 완료, fail은 진행 중으로 되돌리고 사유를 작업자에게 보낸다. 되돌림은 작업마다 두 번까지다. 세 번째 fail은 작업자에게 보내지 않고 **사람 결정 대기**로 옮겨, 작업자 카드에 결정 카드(반려 사유와 완료 기준)를 올린다. 사람이 그 카드로 작업자에게 답장하면 진행 중으로 돌아가고 되돌림 횟수가 처음부터 다시 센다. 사람이 카드를 완료로 기록하면 완료다. 되돌림 메시지의 id는 몇 번째 되돌림인지로 정해, 같은 verify를 다시 실행해도 두 번 보내지 않는다. 작업자의 보고만으로는 완료가 되지 않는다.
- 방치: 진행 중인 작업이 설정의 **작업 방치 기준**(기본 대기 60분, 완료 확인 무응답 30분)을 넘기거나 세션이 사라지면 방치가 된다. 입력 대기(질문, 권한 대기)는 사람의 답이 깨우므로 시간으로는 방치가 되지 않고, 세션이 사라질 때만 방치가 된다. 작업자가 다시 보고하거나 일을 시작하거나, 사람이 보드에서 세션을 열면 진행 중으로 돌아간다.
- 사라진 세션: Orca에서 세션이 사라지면 새로 읽어 한 번 더 확인한 뒤 그 세션의 코디네이터 판단, 카드 기록, 작업자 정보를 지우고 작업 기록을 방치로 바꾼다. 이 확인은 한 곳에서만 하고, 세션이 하나도 없는 목록(Orca 시작, 재시작)은 사라짐으로 세지 않는다.
- 호스트: 설정의 Orca 호스트 목록은 `orca host list`를 읽는다. 짝지은 Orca 환경은 30초에 한 번까지 `orca agent list --environment`로 실행 중 세션을 읽고, 답한 환경만 연결됨으로 본다.
- 프로젝트 아이콘: Orca가 아이콘을 주지 않는 프로젝트는 폴더에서 favicon(PNG, JPEG, WebP, ICO)을 찾는다. SVG는 쓰지 않는다.

## 코디네이터

- **만들기**: 설정에서 고른 모델로 코디네이터를 `orca agent launch --surface terminal`로 띄운다. 기본 위치는 보드의 코디네이터 운영 폴더다(아래). 설정의 "시작할 워크스페이스"에서 다른 워크스페이스를 고르면 그곳에서 시작한다. 응답이 끊겨도 같은 실행을 `--retry-launch`로만 다시 확인하고 두 개를 띄우지 않는다. 터미널이 첫 응답을 하면 보드가 코디네이터로 지정한다. 워크스페이스 고정은 Orca에 없어서 하지 않는다.
- **권한 모드**: 코디네이터는 권한 우회 모드로 띄운다(claude `--dangerously-skip-permissions`, codex `--dangerously-bypass-approvals-and-sandbox`). 에이전트 설정이 이미 붙였으면 그대로 두고, 없으면 한 번 붙인다. Paseo판의 자동 모드(`auto`, `auto-review`)와 다른 점이다.
- **작업자 권한 모드**: 보드가 배정한 작업자는 Paseo의 추천 모드로 띄운다(claude `auto`, codex `auto-review`). 설정에서 claude `default`, codex `auto`, `full-access`로 바꿀 수 있다. 작업자에게는 우회 모드를 주지 않고, 에이전트 설정이 붙인 우회 인자도 뺀다. codex `full-access`(`--sandbox danger-full-access --ask-for-approval never`)만 Paseo처럼 예외로 둔다. 코디네이터의 우회 모드는 사람이 고른 것이고 작업자에게는 넘어가지 않는다.
- **작업자 배정**: `coordinator-board plan`이 관리 프로젝트, 워크스페이스, 등급별 모델과 작업자 권한 모드를 알려 주고, `coordinator-board assign`이 작업자 하나를 띄운다. 실행은 코디네이터 자신의 셸에서 `orca agent launch`로 돈다. 같은 `requestKey`는 두 번 띄우지 않고, 응답이 끊기면 `--retry-launch`로만 다시 확인한다. `job`의 `doneMeans`(완료 기준)는 필수이고, 작업자 프롬프트에 함께 적고 작업 기록에 남긴다. 작업자 프롬프트에는 PR 병합, 기본 브랜치 push, 배포, 비용, 권한 승인은 사람이 정하니 `report --kind question`으로 올리라는 경계도 적는다. Orca가 실행을 거절하면 실행 기록과 작업 기록을 함께 지우고, 결과가 불확실했던 실행을 같은 `requestKey`로 다시 확인할 때 빠진 작업 기록을 채운다. `read`는 작업 기록이 있는 세션에 `work`(단계, 완료 기준, 완료 후보)를 붙인다. 작업자의 등급, 부모(코디네이터), 권한 모드는 보드 데이터 폴더의 `workers.json`에 그 세션 id로 남는다.
- **보고 명령**: Orca 플러그인은 MCP 도구를 줄 수 없어서, 코디네이터는 셸 명령 `coordinator-board`로 보드를 읽고 판단을 남긴다. 모든 에이전트 실행에 `agent.launch.before` 훅이 `CB_*` 변수와 그 터미널 전용 토큰을 넣는다. Windows의 Orca 1.4.277은 훅이 바꾼 PATH를 에이전트 프로세스에 반영하지 않는다. 그래서 charter와 보드가 배정한 작업자의 프롬프트는 명령을 처음부터 절대 경로(`CB_BIN` 폴더의 `coordinator-board`)로 실행하라고 적는다. 명령은 `read [--session]`(목록에서 `"self": true`인 행이 부른 세션 자신), `classify`, `report`, `fact`(다이제스트가 허락한 사실 답장), `review`(병합된 단독 병합 기록 정리와 완료 확인), `plan`, `assign`(작업자 배정), `verify`(완료 보고된 작업 확정)이다. 자세한 쓰임은 `coordinator-board --help`.
- **요청**: 다이제스트, 작업 요청, 추천 요청을 코디네이터에게 보낸다. Orca는 실행 중인 턴에 끼워 넣을 수 없어서 코디네이터가 대기 중일 때만 보낸다. 보드가 쓴 요청에는 `[coordinator-board]` 머리말이 붙는다.
- **채팅 코디네이터**: 기존 채팅 세션을 코디네이터로 고르면 보드가 명령 경로를 한 번 알린다. 채팅은 실행 훅을 거치지 않아 `report`만 쓸 수 있다.
- **코디네이터 운영 폴더**: Paseo판이 플러그인 전용 워크스페이스에서 코디네이터를 만드는 것처럼, 보드는 데이터 폴더 아래 `coordinator` 폴더를 Orca의 폴더 프로젝트로 한 번 등록하고(`orca repo add --kind folder`) 새 코디네이터를 거기서 띄운다. 이미 등록돼 있으면 경로로 찾아 다시 등록하지 않는다. 쓸 때마다 Orca가 보여 주는 값을 읽고, 다를 때만 워크트리 표시를 `show`로, 프로젝트 이름을 "코디네이터 보드", 워크스페이스 이름을 "코디네이터 운영"(보드 언어가 영어면 "Coordinator Board", "Coordinator home")으로 맞춘다. 이 프로젝트는 관리 프로젝트 목록과 세션 레인에 나오지 않지만, 보드가 만든 코디네이터는 그대로 코디네이터로 남는다.
- 채팅 메일을 보내는 보드 터미널은 코디네이터의 워크스페이스에 두고, 코디네이터가 없으면 코디네이터 운영 폴더에 둔다. 사람의 프로젝트에는 열지 않는다.

## 전송 규칙

- 사용자가 쓰고 **보내기**를 누른 글만 보낸다. 그 글은 머리말 없이 그대로 타이핑된다.
- 보내기 직전에 워커가 에이전트 상태를 다시 읽는다. 권한 대기(`blocked`), 작업 중(`working`), 카드를 연 뒤 상태가 바뀐 세션에는 보내지 않는다.
- 터미널 세션에는 `orca terminal send`로 보낸다. 세션이 다른 워크스페이스에 있어도 들어가므로 화면을 옮기지 않는다.
- 닫힌 세션을 이어 열어 보내는 기능은 Paseo판에 없어서 뺐다.
- 실패해도 다시 보내지 않는다.
- 보드가 스스로 만든 문장(사실 답, 병합 알림)은 Paseo판처럼 보낸 쪽을 밝혀 보낸다. 채팅 세션에는 서명한 메일로 보낸다. 사실 답은 코디네이터 터미널, 병합 알림은 보드 메일 터미널이 서명한다. 터미널 세션에는 `[coordinator-board]` 머리말 줄(보낸 쪽 코디네이터 세션 id나 `board`, JSON 문맥)을 붙여 입력한다. Orca 터미널은 메일 본문을 보여 주지 않기 때문이다. 서명할 수 없거나 보내지 못하면 다른 길로 바꿔 보내지 않는다([AGENTS.md](../AGENTS.md) 참고).

## Paseo판과 다른 점

[Paseo판](https://github.com/devbrother2024/paseo-coordinator-board)과 아래가 다르다. Orca가 그 기능을 주지 않아서이고, 보드에서 더 할 일은 없다.

- 워크스페이스 고정: 플러그인 API와 CLI에 고정이 없다. 코디네이터 운영 폴더는 사람이 Orca 사이드바 메뉴의 **고정**으로 직접 고정한다.
- 코디네이터가 작업자에게 넘긴 연결: Orca는 다른 에이전트의 셸에서 띄운 에이전트에 부모를 기록하지 않는다. 보드가 부모를 `workers.json`에 따로 남긴다.
- 끼워 넣기(steer): 실행 중인 턴에 끼워 넣을 수 없다. 받는 세션이 대기 중일 때만 보낸다.
- 터미널이 닫힌 세션에는 보드가 만든 문장(병합 알림, 사실 답)도 보내지 않는다. 입력할 터미널이 없고, 메일은 본문 대신 `orca orchestration check` 알림만 남기기 때문이다. 병합 알림은 Paseo처럼 닫힌 수신자면 `unavailable`이 된다.
- 다른 호스트의 세션 목록 넘겨 보기와 호스트 숨기기. 다른 Orca 환경의 행에는 저장소 이름이 없어서 원격 세션은 같은 저장소 id일 때만 프로젝트에 붙는다.
- 작업자 생성 뒤 권한 모드 확인(`currentModeId`). Orca는 터미널 에이전트의 권한 모드를 알려 주지 않아, 보드는 요청한 모드만 기록한다.

## 실기에서 확인한 Orca 동작 (1.4.272)

- `agents.list`의 `workspaceId`는 `workspace.list`가 주는 id다. 이벤트의 `workspaceId`는 다른 형식(`<uuid>::<경로>`)이라 쓰지 않는다.
- 터미널 수가 0인 워크스페이스에도 에이전트가 있다. 그래서 워크스페이스를 모두 조회한다.
- 터미널 id가 없는 에이전트는 채팅 탭(구조화 세션)이다. 플러그인 API에는 채팅 탭에 글을 넣는 함수가 없다. `agent.resume`은 같은 대화를 새 터미널에서 하나 더 띄우므로 열린 채팅 탭에는 쓰지 않는다. 대신 `workspace.open`으로 그 워크스페이스를 보여 준다. 플러그인은 채팅 탭이 열려 있는지 따로 알 수 없어서, `agents.list`에 있는 세션은 모두 열린 것으로 본다.
- `agents.list`가 `sessionId`를 주지 않는 창이 있다. 그런 창이 있는 워크스페이스의 지난 세션은 이어 열지 않는다.
- `agent.listSessions`는 `history:read`, `agent.resume`은 `agent:launch` 권한이 있어야 한다.
- 0.3.0부터 `agent.launch.before` 훅을 쓴다. 이 버전으로 올리면 권한 목록이 바뀌어 다시 승인해야 한다.
- `terminal.sendText`는 포커스된 워크스페이스의 터미널에만 보낸다(다른 곳이면 `terminal is outside the active worktree`). CLI `orca terminal send`에는 이 제한이 없어서 보드는 CLI로만 보낸다.
- Claude가 평문으로 묻고 턴을 끝내면 상태는 `done`이다. `waiting`은 `AskUserQuestion` 같은 도구로 물을 때 붙는다. 그래서 보드는 Paseo판처럼 `done` 세션의 마지막 답을 읽어(`orca agent read`) 확인 요청 문장이 있으면 사람 레인에 올린다.
- 워크스페이스 id는 `identity:...`, `folder:...`, `<프로젝트>::<경로>` 세 가지 꼴로 온다. 대시보드 명령은 id, 경로, 이름과 브랜치 순서로 포커스된 워크스페이스를 찾는다.
- 커스텀 에디터는 열린 뒤 `orca.document.get()`으로 파일을 한 번 요청해야 한다. 요청하지 않으면 Orca가 에디터를 다 열리지 않은 것으로 본다.
- 워커 프로세스에는 `APPDATA`와 `HOME`이 없다. Windows의 `gh`는 `%APPDATA%\\GitHub CLI`에서 로그인 정보를 읽으므로, 워커가 `USERPROFILE`로 채워서 실행한다(`commandEnv`).

## 실기에서 확인한 orca CLI 동작 (1.4.277)

- `orca worktree ps --json` 한 번에 워크스페이스, 에이전트, 터미널 주소(`term_…`), 마지막 턴 결과(`mainAgent.outcome`), 안 읽음(`activity.unread`)이 함께 온다. 보드는 스냅샷마다 이것을 한 번 읽는다.
- 처음 보고하기 전의 터미널 에이전트는 `orcaSessionId`가 없다. 보드는 이런 행을 세기만 하고 올리지 않는다.
- 터미널 세션의 `orca agent read`는 긴 항목을 약 1,200자에서 자르고 `… (truncated)`를 붙인다. 같은 세션의 `worktree ps` 행은 마지막 답을 통째로 주므로, 앞부분이 같으면 그 글로 되돌린다. 채팅 기록은 자르지 않는다.
- 같은 대화가 두 창에 보일 때가 있다. 보드는 목록에 보이는 쪽, 그다음 최근 쪽을 쓴다.

코디네이터 채널은 `node scripts/probe-channel.mjs`로 확인한다(빌드 뒤). 실제 워커 코드의 실행 훅을 부르고 그 env로 `bin/coordinator-board`를 실행해 종료 코드를 출력한다. 보드 데이터는 임시 폴더에 둔다.

장부, 사실, PR은 `node scripts/probe-ledger.mjs prs|mail|review`로 확인한다(사용법은 파일 머리). `prs`는 읽기만 하고 병합은 확정하지 않는다. 실행 중인 에이전트가 받은 PATH 키와 `CB_*` 변수는 `node scripts/probe-path.mjs --match <명령 줄의 글>`로 읽기만 해서 본다(값은 출력하지 않는다).

실제 세션으로 스냅샷을 만들어 보려면 `node scripts/probe-snapshot.mjs`를 돌린다. 모든 프로젝트를 고른 상태로 레인별 수, 사람 레인 세션, CLI 호출 수와 시간을 출력한다. 출력에 실제 세션 이름이 나오니 저장소에 남기지 않는다.
